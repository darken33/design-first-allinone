# Contracts – HelloAPI Node.js

**Purpose**: Define all external contracts (APIs, DTOs, interfaces) that clients and consumers must respect.

**Status**: v1.0.0 (Phase 1 Design)

---

## Contract Overview

HelloAPI exposes 3 types of contracts:

### 1. **HTTP API Contract** → [api.md](./api.md)
- **Audience**: Frontend, mobile apps, API consumers
- **Format**: OpenAPI 3.0 YAML (source of truth)
- **Endpoints**: 3 (GET /api/v1/hello, GET /api/v1/hello/{name}, GET /health)
- **Transport**: HTTP/REST
- **Stability**: Production-ready

### 2. **Data Contracts** → [data.md](./data.md)
- **Audience**: Integrations, code generators
- **Format**: TypeScript interfaces + Zod schemas
- **Models**: HelloDto, HealthDto, ApiErrorResponse
- **Generation**: Auto-generated by orval from OpenAPI
- **Stability**: Mirrors HTTP API contract stability

### 3. **Service Interface Contract** → [service.md](./service.md)
- **Audience**: Internal developers (implementing services)
- **Format**: TypeScript interface definitions
- **Services**: IHelloService, IHealthService
- **Consumers**: Controllers, aggregators
- **Stability**: Internal (can evolve with deprecation warnings)

## Key Principles

### Contract-First Design

All contracts are **derived from OpenAPI specification**:

```
OpenAPI Spec (specs/001-hello-api-node/openapi.yaml)
    ↓
    ├─→ HTTP Contract (api.md) — What HTTP clients see
    ├─→ Data Contracts (data.md) — Auto-generated types via orval
    └─→ Service Contract (service.md) — Internal service boundary
```

### Immutability During MVP

**During MVP phase (Phase 2)**: Contracts are **READ-ONLY** from implementation perspective:
- HTTP API contract defined by OpenAPI spec (ratified in Phase 1)
- Data contracts auto-generated (no manual editing)
- Service contracts designed in Phase 1 (locked for Phase 2)

**Rationale**: Prevents implementation drift; enforces spec compliance from day 1.

### Contract Evolution Workflow

Post-MVP (Phase 3+):
1. **API changes proposed** → Update OpenAPI spec
2. **spec.md updated** with rationale → Review requirement impact
3. **Data contracts regenerated** from new OpenAPI
4. **Service contracts evolved** (with deprecation period if public)
5. **Implementation updated** to new contract
6. **Tests + integration tests** reverify compliance
7. **Version bumped** (Semantic Versioning)

## Validation Checklist

Before implementation (Phase 2), verify:

- [ ] OpenAPI spec is syntactically valid (Swagger Editor passes)
- [ ] OpenAPI spec matches requirements in spec.md
- [ ] All HTTP response codes documented in OpenAPI
- [ ] All validation rules (name parameter) encoded in OpenAPI
- [ ] Data contracts (DTOs) match OpenAPI schemas exactly
- [ ] Service contracts (interfaces) defined and consistent
- [ ] Error response structure defined (ApiErrorResponse)
- [ ] Documentation is complete and examples run
