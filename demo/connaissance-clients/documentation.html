🔗API REST
GET /v1/connaissance-clients
🔓 Aucune auth requise
Récupère la liste complète des fiches de connaissance client disponibles.
Retourne un tableau JSON (liste vide si aucun client enregistré).

Cas d'usage : affichage de la liste des clients pour sélection, export de données, recherche globale.
Performance : limite recommandée — utiliser la pagination pour de gros volumes. Temps de réponse typique < 2 s.

POST /v1/connaissance-clients
🔒 Bearer JWT
Crée une nouvelle fiche de connaissance client dans le système.

Cas d'usage : enregistrement d'un nouveau client lors de l'onboarding, import depuis un système externe, saisie manuelle par un conseiller.
Règles métier : un client ne peut avoir qu'une seule fiche active. Les informations personnelles sont chiffrées en base.
Résultat : la fiche créée est retournée avec son ID généré. Un événement de création est émis pour notification.

DELETE /v1/connaissance-clients/{id}
🔒 Bearer JWT
⚠️ Opération irréversible. La suppression est définitive et entraîne la suppression en cascade des données liées.
Supprime définitivement une fiche de connaissance client du système.

Cas d'usage : suppression demandée par le client (RGPD / droit à l'oubli), nettoyage de doublons, archivage avec suppression des données sensibles.
Sécurité : vérification des droits de suppression, audit trail obligatoire, confirmation requise pour les comptes actifs.
Conformité : conforme RGPD, respect des délais de conservation légaux. Archive des métadonnées pour audit (sans données personnelles).

PUT /v1/connaissance-clients/{id}/adresse
🔒 Bearer JWT
✅ Bonne pratique REST : PUT est utilisé pour la modification complète de la sous-ressource adresse. Seule l'adresse est modifiée — nom, prénom et situation familiale restent inchangés.
Modifie uniquement l'adresse d'une fiche de connaissance client existante.

Cas d'usage : déménagement du client, correction d'une adresse erronée, mise à jour suite à un changement de domicile.
Validation externe : l'adresse est validée via l'API IGN (cohérence code postal / ville). En cas d'échec, erreur 422.
Résilience : circuit breaker actif pour l'API IGN (3 échecs consécutifs → skip pendant 60 s).
Événement : un message Kafka est publié sur le topic event.adresse.v1 après modification réussie.
Performance : temps de réponse typique < 2 s (avec validation API IGN).

PUT /v1/connaissance-clients/{id}/situation
🔒 Bearer JWT
✅ Bonne pratique REST : PUT est utilisé pour la modification complète de la sous-ressource situation. Seule la situation familiale est modifiée — nom, prénom et adresse restent inchangés.
Modifie uniquement la situation familiale et le nombre d'enfants d'un client existant.

Cas d'usage : changement d'état civil (mariage, divorce, veuvage), naissance ou adoption d'enfant(s), mise à jour suite à un événement de vie.
Règles métier : un client célibataire peut avoir des enfants (garde alternée, adoption). Le nombre d'enfants peut être 0 même si marié. La situation PACSE est acceptée.
Pas d'événement Kafka : aucun message n'est publié pour ce type de modification.
Performance : temps de réponse typique < 100 ms (pas de validation externe).

Un événement Kafka est publié sur le topic event.adresse.v1 à chaque modification d'adresse réussie via PUT /v1/connaissance-clients/{id}/adresse.
Aucun événement n'est publié pour la modification de situation familiale.
